Architectural Guide to Uniform Resource Identifier (URI) Percent-Encoding and Query Parameter Parsing

An exhaustive engineering examination of IETF RFC 3986, the WHATWG URL Standard, character set limitations, security attack vectors, and component-level escaping mechanics.

1. Architectural Foundations of Uniform Resource Identifiers and RFC 3986

Every networked interaction across modern computing relies on Uniform Resource Identifiers (URIs) to locate, name, and interact with network resources. Formalized by Tim Berners-Lee, Roy Fielding, and Larry Masinter within the Internet Engineering Task Force (IETF) Request for Comments 3986 (RFC 3986, Standard 66), a URI establishes a consistent, unambiguous grammar capable of expressing references across distinct naming authorities and transmission protocols.

The generic syntax established by RFC 3986 section 3 defines a five-component hierarchical structure:

URI = scheme ":" hier-part [ "?" query ] [ "#" fragment ]

The hierarchical segment (hier-part) begins with an optional double slash followed by the authority component, which itself partitions into [ userinfo "@" ] host [ ":" port ], followed by the path segment. The query component, introduced by a leading question mark (?), provides non-hierarchical identification data frequently represented as key-value tuples. Finally, the fragment component, prefixed by a hash symbol (#), designates a secondary sub-resource processed exclusively on the client device without transmission across HTTP request lines.

Because specific ASCII symbols serve as structural boundary markers, software decoders must distinguish between delimiters that structure the URI and literal data characters contained within each constituent part. This absolute requirement creates the foundation for percent-encoding.

2. Character Sets, US-ASCII Restrictions, and UTF-8 Octet Representation

The fundamental constraint of internet addressing stems from early transmission channels that supported only 7-bit US-ASCII character representations. To guarantee that identifiers pass unharmed through heterogeneous gateways, proxies, email systems, and terminal controllers, RFC 3986 section 2 explicitly restricts the permitted character set of any valid URI to a rigorous subset of US-ASCII.

When an application requires characters outside this permitted set, or characters that conflict with designated structural roles, it must apply percent-encoding (often termed URL encoding). A percent-encoding consists of a three-character sequence: the percent character % followed by two hexadecimal digits that express the numeric value of the underlying octet (byte).

In legacy standards like RFC 1738, percent-encoding operated on isolated byte streams without defining a universal character encoding. This historical omission led to severe internationalization incompatibilities across platforms that interpreted non-ASCII bytes under disparate local code pages (such as Windows-1252, ISO-8859-1, or Shift-JIS). To resolve this ambiguity, RFC 3986 section 2.5 and RFC 3987 (Internationalized Resource Identifiers) standardized that characters outside US-ASCII must first be mapped to an octet sequence according to the UTF-8 transformation format before percent-encoding each byte individually:

  • Single-byte ASCII Range (U+0000 to U+007F): Standard ASCII characters map directly to a single byte. For example, a blank space has hexadecimal code point 0x20 and encodes as %20.
  • Two-byte Unicode Range (U+0080 to U+07FF): Accented Latin, Greek, and Cyrillic characters require two bytes. The character é (U+00E9) maps to UTF-8 bytes 0xC3 0xA9 and encodes as %C3%A9.
  • Three-byte Unicode Range (U+0800 to U+FFFF): CJK ideographs and Arabic glyphs require three bytes. The kanji character 文 (U+6587) decomposes into 0xE6 0x96 0x87 and encodes as %E6%96%87.
  • Four-byte Supplementary Astral Plane (U+10000 to U+10FFFF): Complex emojis and historical scripts consume four bytes. The rocket emoji 🚀 (U+1F680) maps to 0xF0 0x9F 0x9A 0x80 and encodes as %F0%9F%9A%80.

Per RFC 3986 section 6.2.2.1, the hexadecimal letters A through F within percent-encodings are case-insensitive. However, canonical normalization routines require uppercase representations to maintain byte-level determinism during cache indexing and cryptographic signature validation.

3. The RFC 3986 Character Classification Matrix: Reserved vs Unreserved

RFC 3986 section 2 partitions the entire ASCII spectrum into distinct functional categories that dictate whether a character may appear verbatim or must undergo escaping:

Category Character Set Architectural Purpose & Rule
Unreserved A-Z a-z 0-9 - . _ ~ Characters that have identical semantics whether encoded or unencoded. RFC 3986 mandates producers must not percent-encode these characters.
Reserved: gen-delims : / ? # [ ] @ General delimiters that establish structural component boundaries (scheme colon, path slashes, query mark, fragment hash).
Reserved: sub-delims ! $ & ' ( ) * + , ; = Sub-delimiters used to structure internal component data (ampersand and equals sign in query string parameter lists).
Disallowed / Unsafe space " < > % \ ^ ` { | } Characters that cause visual ambiguity, gateway parsing failure, or control sequence collision. Must always be percent-encoded.

When a reserved character appears within a component to represent literal data rather than a structural delimiter, it must be percent-encoded. For instance, if a search query value contains an ampersand (such as Barnes & Noble), transmitting an unencoded & would cause compliant query parsers to split the string into two distinct parameters (q=Barnes and a spurious parameter Noble). Escaping the character as %26 preserves the ampersand as literal payload text.

4. Comparative Analysis: encodeURI() versus encodeURIComponent()

A frequent source of software defects in modern web applications arises from the misunderstanding of native ECMAScript encoding primitives: encodeURI() and encodeURIComponent(). While both functions generate percent-encoded representations, their operational assumptions address fundamentally different scopes:

The Operational Purpose of encodeURI(): This function is designed to process an entire, complete Uniform Resource Identifier string. Its primary objective is to make the string transmission-safe while preserving every structural delimiter that defines the URL's anatomy. Consequently, encodeURI() does not encode the 11 reserved characters:

; / ? : @ & = + $ , #

If encodeURI() were to escape forward slashes or colons, the resultant string https%3A%2F%2Fexample.com%2Fpath would cease to be recognizable as a functional HTTP locator by web browsers or transport clients.

The Operational Purpose of encodeURIComponent(): In sharp contrast, this function operates on isolated individual components, such as a solitary path segment, a query parameter key, or a query parameter value. It assumes that any character passed into it represents literal payload data rather than a structural separator. Therefore, encodeURIComponent() percent-encodes all 11 reserved delimiters listed above, transforming forward slashes into %2F, ampersands into %26, equals signs into %3D, and question marks into %3F.

The ECMAScript Non-Compliance Anomaly: Software engineers must recognize that neither standard JavaScript function is fully compliant with RFC 3986 section 2.3. Both functions fail to percent-encode five specific characters:

! ' ( ) *

Because these symbols belong to the sub-delims set under RFC 3986, leaving them unescaped can cause downstream parsing failures in protocols that treat parentheses or asterisks as boundary tokens. To achieve strict RFC 3986 compliance, developers apply a post-processing regular expression replacement:

function strictEncodeRFC3986(str) {
  return encodeURIComponent(str).replace(/[!'()*]/g, function(c) {
    return '%' + c.charCodeAt(0).toString(16).toUpperCase();
  });
}

5. The application/x-www-form-urlencoded Standard versus RFC 3986

A persistent divergence in web development exists between generic RFC 3986 URI parsing and HTML form encoding governed by the MIME media type application/x-www-form-urlencoded (maintained under the WHATWG URL Living Standard).

The primary divergence centers on the space character. In RFC 3986, the space character possesses octet value 0x20 and must always be percent-encoded as %20. However, the early HTML 2.0 specification specified that spaces in form submission queries should be converted into plus signs (+) to improve terminal legibility, reserving %2B for actual literal plus signs.

This historical design creates severe decoding ambiguities in modern REST APIs. If a client transmits a literal plus sign without percent-encoding (such as an international telephone number +14155550199 or a Base64 string eyJh...u8+3), form-aware backend decoders convert that plus sign into an unintended space character ( 14155550199), corrupting data integrity. Systems implementing RFC 3986 avoid this defect by uniformly encoding literal plus signs as %2B and spaces as %20.

6. Security Vulnerabilities: Injection, Traversal, and Double Encoding

Improper handling of URL percent-encoding represents one of the most persistent classes of software vulnerabilities in networked computing. Because decoding transforms strings across application layers, subtle architectural mismatches introduce critical attack vectors:

Path and Directory Traversal Exploits

In a directory traversal attack, an adversary seeks to escape the designated web document root and access sensitive operating system files (such as /etc/passwd or configuration files). While simple perimeter filters inspect requests for literal dot-dot-slash patterns (../), attackers submit percent-encoded representations:

%2e%2e%2f          (Standard hexadecimal encoding of ../)
%2e%2e/            (Mixed literal and encoded dots)
%2e%2e%5c          (Windows directory separator ..\)

If an application runtime performs access validation before decoding the incoming URL path, the perimeter filter inspects the unescaped hex characters and marks the request benign. Once passed to the file handling subsystem, secondary decoding resolves %2e%2e%2f into literal directory traversal, compromising system isolation.

Double Percent-Encoding Attacks

In modern enterprise cloud architectures, requests traverse multiple routing tiers: an edge content delivery network (CDN), an ingress Web Application Firewall (WAF), an API gateway, and microservice backends. Double percent-encoding exploits this multi-tier pipeline.

An attacker submits a double-encoded sequence such as %252e%252e%252f. Here, the percent character itself is encoded as %25. When the front-end WAF inspects the payload, it decodes the input once, transforming %252e into %2e. Finding no literal traversal markers, the firewall permits the request. Downstream, an application server or framework middleware decodes the parameter a second time, converting %2e%2e%2f into ../ and executing the unauthorized file read.

HTTP Parameter Pollution (HPP) and Query Injection

When user input intended for a query value contains unencoded ampersands (&) or equals signs (=), the input stream injects additional parameters directly into the server's parameter dictionary. In addition, when multiple parameters share identical keys (e.g. id=1&id=2), different web server runtimes exhibit conflicting parsing behaviors:

  • Apache Tomcat / PHP: Preserves only the last parameter instance (id=2).
  • Microsoft ASP.NET / IIS: Concatenates instances with a comma (id=1,2).
  • Node.js (Express / qs): Constructs an array data structure (id=['1', '2']).

Adversaries exploit these divergent interpretations to bypass front-end input validation filters while delivering malicious inputs to backend databases.

Null Byte Injection and CRLF Splitting

Submitting a percent-encoded null byte (%00) historically allowed attackers to exploit C/C++ string termination semantics within underlying system libraries, causing file path checks to truncate strings prematurely (e.g., passing image.png%00.php to bypass extension whitelists). Similarly, injecting carriage return and line feed bytes (%0d%0a) into parameter values reflected in HTTP response headers enables HTTP response splitting and cache poisoning.

7. Authoritative Standards Evolution: RFC 1738, RFC 3986, and WHATWG

The governance of URL mechanics has evolved across three major engineering eras:

IETF RFC 1738 (1994): Drafted by Berners-Lee, Masinter, and McCahill, RFC 1738 served as the foundational Uniform Resource Locators standard. It defined initial protocol schemes (http, ftp, mailto) and established basic percent-hex escaping, but lacked a rigorous generic decomposition model.

IETF RFC 3986 (2005): The definitive Internet Standard (STD 66) authored by Berners-Lee, Fielding, and Masinter. RFC 3986 introduced the universal ABNF grammar for URI decomposition, standardized the unreserved character set, partitioned delimiters into gen-delims and sub-delims, and established clear canonicalization criteria.

The WHATWG URL Living Standard: In recent years, browser vendors recognized that real-world web implementations contained numerous undocumented parsing quirks and legacy error-handling tolerances not codified in RFC 3986. The Web Hypertext Application Technology Working Group (WHATWG) developed the URL Living Standard to define exact algorithmic state machines for URL parsing, normalization, and the URLSearchParams browser API. Modern web engineering relies on RFC 3986 for network protocol design and the WHATWG standard for browser DOM runtime fidelity.

Technical Inquiries

Frequently Asked Questions

The primary distinction centers on delimiter preservation. encodeURI is engineered for full Uniform Resource Identifiers and preserves protocol, path, query, and fragment delimiters including colon, slash, question mark, ampersand, hash, and equals sign. encodeURIComponent is designed for isolated components (such as query parameter values) and percent-encodes these delimiters so they do not alter the structural hierarchy of the parent URL.

RFC 3986 dictates that spaces must be percent-encoded as %20 across all URI components. The plus sign convention originates from the HTML application/x-www-form-urlencoded media type, which historically substituted spaces with plus signs to improve legibility in query strings. Modern web standards require strict %20 encoding for generic URI components, whereas HTML form decoders interpret plus signs as spaces.

Percent-encoding operates at the binary octet level. Characters beyond the 7-bit US-ASCII set are first encoded into their UTF-8 byte representation, which requires two, three, or four bytes per code point. Each individual byte is then represented by a percent sign followed by two hexadecimal digits. For instance, the rocket emoji U+1F680 decomposes into four UTF-8 bytes (F0 9F 9A 80) and encodes as %F0%9F%9A%80.

RFC 3986 defines unreserved characters as uppercase letters (A-Z), lowercase letters (a-z), decimal digits (0-9), hyphen (-), period (.), low line symbol (_), and tilde (~). These characters have identical semantics whether encoded or unencoded, and RFC 3986 explicitly advises URI producers against percent-encoding them.

A double percent-encoding vulnerability occurs in multi-tiered architectures where an intermediate security layer, such as a Web Application Firewall, decodes an input once while a downstream backend application decodes it a second time. An attacker can submit %252e%252e%252f; the firewall decodes %25 into a percent symbol, yielding %2e%2e%2f (which passes inspection), and the backend decodes that string into ../ to execute unauthorized directory traversal.

JavaScript encodeURI and encodeURIComponent adhere to older ECMAScript specifications that preserved characters like exclamation mark (!), single quote ('), opening parenthesis ((), closing parenthesis ()), and asterisk (*) for historical compatibility. Because these characters are classified as sub-delimiters under RFC 3986 section 2.2, strict RFC 3986 compliance requires an additional programmatic replacement step to convert them into %21, %27, %28, %29, and %2A.

An attacker submits a double-encoded sequence such as %252e%252e%252f. Here, the percent character itself is encoded as %25. When the front-end WAF inspects the payload, it decodes the input once, transforming %252e into %2e. Finding no literal traversal markers, the firewall permits the request. Downstream, an application server or framework middleware decodes the parameter a second time, converting %2e%2e%2f into ../ and executing the unauthorized file read.

HTTP Parameter Pollution (HPP) and Query Injection

When user input intended for a query value contains unencoded ampersands (&) or equals signs (=), the input stream injects additional parameters directly into the server's parameter dictionary. In addition, when multiple parameters share identical keys (e.g. id=1&id=2), different web server runtimes exhibit conflicting parsing behaviors:

  • Apache Tomcat / PHP: Preserves only the last parameter instance (id=2).
  • Microsoft ASP.NET / IIS: Concatenates instances with a comma (id=1,2).
  • Node.js (Express / qs): Constructs an array data structure (id=['1', '2']).

Adversaries exploit these divergent interpretations to bypass front-end input validation filters while delivering malicious inputs to backend databases.

Null Byte Injection and CRLF Splitting

Submitting a percent-encoded null byte (%00) historically allowed attackers to exploit C/C++ string termination semantics within underlying system libraries, causing file path checks to truncate strings prematurely (e.g., passing image.png%00.php to bypass extension whitelists). Similarly, injecting carriage return and line feed bytes (%0d%0a) into parameter values reflected in HTTP response headers enables HTTP response splitting and cache poisoning.

7. Authoritative Standards Evolution: RFC 1738, RFC 3986, and WHATWG

The governance of URL mechanics has evolved across three major engineering eras:

IETF RFC 1738 (1994): Drafted by Berners-Lee, Masinter, and McCahill, RFC 1738 served as the foundational Uniform Resource Locators standard. It defined initial protocol schemes (http, ftp, mailto) and established basic percent-hex escaping, but lacked a rigorous generic decomposition model.

IETF RFC 3986 (2005): The definitive Internet Standard (STD 66) authored by Berners-Lee, Fielding, and Masinter. RFC 3986 introduced the universal ABNF grammar for URI decomposition, standardized the unreserved character set, partitioned delimiters into gen-delims and sub-delims, and established clear canonicalization criteria.

The WHATWG URL Living Standard: In recent years, browser vendors recognized that real-world web implementations contained numerous undocumented parsing quirks and legacy error-handling tolerances not codified in RFC 3986. The Web Hypertext Application Technology Working Group (WHATWG) developed the URL Living Standard to define exact algorithmic state machines for URL parsing, normalization, and the URLSearchParams browser API. Modern web engineering relies on RFC 3986 for network protocol design and the WHATWG standard for browser DOM runtime fidelity.

Network Protocol Architecture & URI Specification

Architectural Guide to Uniform Resource Identifier (URI) Percent-Encoding and Query Parameter Parsing

An exhaustive engineering examination of IETF RFC 3986, the WHATWG URL Standard, character set limitations, security attack vectors, and component-level escaping mechanics.

1. Architectural Foundations of Uniform Resource Identifiers and RFC 3986

Every networked interaction across modern computing relies on Uniform Resource Identifiers (URIs) to locate, name, and interact with network resources. Formalized by Tim Berners-Lee, Roy Fielding, and Larry Masinter within the Internet Engineering Task Force (IETF) Request for Comments 3986 (RFC 3986, Standard 66), a URI establishes a consistent, unambiguous grammar capable of expressing references across distinct naming authorities and transmission protocols.

The generic syntax established by RFC 3986 section 3 defines a five-component hierarchical structure:

URI = scheme ":" hier-part [ "?" query ] [ "#" fragment ]

The hierarchical segment (hier-part) begins with an optional double slash followed by the authority component, which itself partitions into [ userinfo "@" ] host [ ":" port ], followed by the path segment. The query component, introduced by a leading question mark (?), provides non-hierarchical identification data frequently represented as key-value tuples. Finally, the fragment component, prefixed by a hash symbol (#), designates a secondary sub-resource processed exclusively on the client device without transmission across HTTP request lines.

Because specific ASCII symbols serve as structural boundary markers, software decoders must distinguish between delimiters that structure the URI and literal data characters contained within each constituent part. This absolute requirement creates the foundation for percent-encoding.

2. Character Sets, US-ASCII Restrictions, and UTF-8 Octet Representation

The fundamental constraint of internet addressing stems from early transmission channels that supported only 7-bit US-ASCII character representations. To guarantee that identifiers pass unharmed through heterogeneous gateways, proxies, email systems, and terminal controllers, RFC 3986 section 2 explicitly restricts the permitted character set of any valid URI to a rigorous subset of US-ASCII.

When an application requires characters outside this permitted set, or characters that conflict with designated structural roles, it must apply percent-encoding (often termed URL encoding). A percent-encoding consists of a three-character sequence: the percent character % followed by two hexadecimal digits that express the numeric value of the underlying octet (byte).

In legacy standards like RFC 1738, percent-encoding operated on isolated byte streams without defining a universal character encoding. This historical omission led to severe internationalization incompatibilities across platforms that interpreted non-ASCII bytes under disparate local code pages (such as Windows-1252, ISO-8859-1, or Shift-JIS). To resolve this ambiguity, RFC 3986 section 2.5 and RFC 3987 (Internationalized Resource Identifiers) standardized that characters outside US-ASCII must first be mapped to an octet sequence according to the UTF-8 transformation format before percent-encoding each byte individually:

  • Single-byte ASCII Range (U+0000 to U+007F): Standard ASCII characters map directly to a single byte. For example, a blank space has hexadecimal code point 0x20 and encodes as %20.
  • Two-byte Unicode Range (U+0080 to U+07FF): Accented Latin, Greek, and Cyrillic characters require two bytes. The character é (U+00E9) maps to UTF-8 bytes 0xC3 0xA9 and encodes as %C3%A9.
  • Three-byte Unicode Range (U+0800 to U+FFFF): CJK ideographs and Arabic glyphs require three bytes. The kanji character 文 (U+6587) decomposes into 0xE6 0x96 0x87 and encodes as %E6%96%87.
  • Four-byte Supplementary Astral Plane (U+10000 to U+10FFFF): Complex emojis and historical scripts consume four bytes. The rocket emoji 🚀 (U+1F680) maps to 0xF0 0x9F 0x9A 0x80 and encodes as %F0%9F%9A%80.

Per RFC 3986 section 6.2.2.1, the hexadecimal letters A through F within percent-encodings are case-insensitive. However, canonical normalization routines require uppercase representations to maintain byte-level determinism during cache indexing and cryptographic signature validation.

3. The RFC 3986 Character Classification Matrix: Reserved vs Unreserved

RFC 3986 section 2 partitions the entire ASCII spectrum into distinct functional categories that dictate whether a character may appear verbatim or must undergo escaping:

Category Character Set Architectural Purpose & Rule
Unreserved A-Z a-z 0-9 - . _ ~ Characters that have identical semantics whether encoded or unencoded. RFC 3986 mandates producers must not percent-encode these characters.
Reserved: gen-delims : / ? # [ ] @ General delimiters that establish structural component boundaries (scheme colon, path slashes, query mark, fragment hash).
Reserved: sub-delims ! $ & ' ( ) * + , ; = Sub-delimiters used to structure internal component data (ampersand and equals sign in query string parameter lists).
Disallowed / Unsafe space " < > % \ ^ ` { | } Characters that cause visual ambiguity, gateway parsing failure, or control sequence collision. Must always be percent-encoded.

When a reserved character appears within a component to represent literal data rather than a structural delimiter, it must be percent-encoded. For instance, if a search query value contains an ampersand (such as Barnes & Noble), transmitting an unencoded & would cause compliant query parsers to split the string into two distinct parameters (q=Barnes and a spurious parameter Noble). Escaping the character as %26 preserves the ampersand as literal payload text.

4. Comparative Analysis: encodeURI() versus encodeURIComponent()

A frequent source of software defects in modern web applications arises from the misunderstanding of native ECMAScript encoding primitives: encodeURI() and encodeURIComponent(). While both functions generate percent-encoded representations, their operational assumptions address fundamentally different scopes:

The Operational Purpose of encodeURI(): This function is designed to process an entire, complete Uniform Resource Identifier string. Its primary objective is to make the string transmission-safe while preserving every structural delimiter that defines the URL's anatomy. Consequently, encodeURI() does not encode the 11 reserved characters:

; / ? : @ & = + $ , #

If encodeURI() were to escape forward slashes or colons, the resultant string https%3A%2F%2Fexample.com%2Fpath would cease to be recognizable as a functional HTTP locator by web browsers or transport clients.

The Operational Purpose of encodeURIComponent(): In sharp contrast, this function operates on isolated individual components, such as a solitary path segment, a query parameter key, or a query parameter value. It assumes that any character passed into it represents literal payload data rather than a structural separator. Therefore, encodeURIComponent() percent-encodes all 11 reserved delimiters listed above, transforming forward slashes into %2F, ampersands into %26, equals signs into %3D, and question marks into %3F.

The ECMAScript Non-Compliance Anomaly: Software engineers must recognize that neither standard JavaScript function is fully compliant with RFC 3986 section 2.3. Both functions fail to percent-encode five specific characters:

! ' ( ) *

Because these symbols belong to the sub-delims set under RFC 3986, leaving them unescaped can cause downstream parsing failures in protocols that treat parentheses or asterisks as boundary tokens. To achieve strict RFC 3986 compliance, developers apply a post-processing regular expression replacement:

function strictEncodeRFC3986(str) {
  return encodeURIComponent(str).replace(/[!'()*]/g, function(c) {
    return '%' + c.charCodeAt(0).toString(16).toUpperCase();
  });
}

5. The application/x-www-form-urlencoded Standard versus RFC 3986

A persistent divergence in web development exists between generic RFC 3986 URI parsing and HTML form encoding governed by the MIME media type application/x-www-form-urlencoded (maintained under the WHATWG URL Living Standard).

The primary divergence centers on the space character. In RFC 3986, the space character possesses octet value 0x20 and must always be percent-encoded as %20. However, the early HTML 2.0 specification specified that spaces in form submission queries should be converted into plus signs (+) to improve terminal legibility, reserving %2B for actual literal plus signs.

This historical design creates severe decoding ambiguities in modern REST APIs. If a client transmits a literal plus sign without percent-encoding (such as an international telephone number +14155550199 or a Base64 string eyJh...u8+3), form-aware backend decoders convert that plus sign into an unintended space character ( 14155550199), corrupting data integrity. Systems implementing RFC 3986 avoid this defect by uniformly encoding literal plus signs as %2B and spaces as %20.

6. Security Vulnerabilities: Injection, Traversal, and Double Encoding

Improper handling of URL percent-encoding represents one of the most persistent classes of software vulnerabilities in networked computing. Because decoding transforms strings across application layers, subtle architectural mismatches introduce critical attack vectors:

Path and Directory Traversal Exploits

In a directory traversal attack, an adversary seeks to escape the designated web document root and access sensitive operating system files (such as /etc/passwd or configuration files). While simple perimeter filters inspect requests for literal dot-dot-slash patterns (../), attackers submit percent-encoded representations:

%2e%2e%2f          (Standard hexadecimal encoding of ../)
%2e%2e/            (Mixed literal and encoded dots)
%2e%2e%5c          (Windows directory separator ..\)

If an application runtime performs access validation before decoding the incoming URL path, the perimeter filter inspects the unescaped hex characters and marks the request benign. Once passed to the file handling subsystem, secondary decoding resolves %2e%2e%2f into literal directory traversal, compromising system isolation.

Double Percent-Encoding Attacks

In modern enterprise cloud architectures, requests traverse multiple routing tiers: an edge content delivery network (CDN), an ingress Web Application Firewall (WAF), an API gateway, and microservice backends. Double percent-encoding exploits this multi-tier pipeline.

An attacker submits a double-encoded sequence such as %252e%252e%252f. Here, the percent character itself is encoded as %25.
